# 服务器端协议升级需求 - v5.0 到 v5.2

> 版本：v1.0  
> 日期：2026-01-16  
> 状态：待实现

---

## 一、升级概述

本文档对比分析服务器端协议规范 v5.0 与 ESP32 端协议规范 v5.2 的差异，列出服务器端需要进行的更新。

**ESP32 端已完成的升级：**
- v5.1：两级确认机制、统一错误码、新增消息类型
- v5.2：新增 query 消息、face_result 两级确认

---

## 二、关键差异汇总

| 差异项 | 服务器 v5.0 | ESP32 v5.2 | 影响 |
|--------|-------------|------------|------|
| 消息 ID 字段名 | `msg_id` | `seq_id`（兼容 `msg_id`） | 建议统一使用 `seq_id` |
| 确认机制 | 单级 `ack` | 两级 `esp32_ack` + `ack` | 需要处理新消息类型 |
| 错误码定义 | 0-7 | 0-10 | 需要更新错误码表 |
| log_report 格式 | `result: bool` | `status: string` + `lock_time` | 需要更新解析逻辑 |
| 新增消息类型 | - | `esp32_ack`, `door_opened_report`, `password_report`, `query` | 需要添加处理器 |
| 新增事件类型 | - | `door_closed`, `lock_success`, `bolt_alarm` | 需要更新事件处理 |

---

## 三、详细修改清单

### 3.1 消息 ID 字段名统一

**当前状态（v5.0）**：使用 `msg_id`

**目标状态（v5.2）**：使用 `seq_id`（兼容 `msg_id`）

**修改内容**：

1. **下发命令时**：将 `msg_id` 改为 `seq_id`
   ```json
   // v5.0
   { "type": "lock_control", "msg_id": "cmd_1001", ... }
   
   // v5.2
   { "type": "lock_control", "seq_id": "1702234567890_0", ... }
   ```

2. **seq_id 格式建议**：`时间戳_序号`（如 `1702234567890_0`）

3. **涉及文件**：
   - 所有下发命令的代码
   - `lock_control`, `dev_control`, `user_mgmt`, `face_result` 消息构建

---

### 3.2 两级确认机制

**当前状态（v5.0）**：只处理 `ack` 消息

**目标状态（v5.2）**：处理 `esp32_ack` + `ack` 两级确认

#### 3.2.1 新增 esp32_ack 处理

**消息格式**：
```json
{
    "type": "esp32_ack",
    "seq_id": "1702234567890_0",
    "code": 0,
    "msg": "received"
}
```

**含义**：ESP32 已收到命令，开始处理

**服务器处理逻辑**：
1. 记录命令已被 ESP32 接收
2. 可选：转发给 App（通知"命令已送达"）
3. 继续等待最终 `ack`

**涉及文件**：
- 新增 `core/handle/textHandler/esp32AckHandler.py`

#### 3.2.2 更新 ack 处理

**消息格式**：
```json
{
    "type": "ack",
    "seq_id": "1702234567890_0",
    "code": 0,
    "msg": "OK"
}
```

**含义**：命令执行完成

**服务器处理逻辑**：
1. 记录命令执行结果
2. 转发给 App（通知"命令执行完成"）

**涉及文件**：
- 更新 `core/handle/textHandler/ackHandler.py`
- 字段名从 `msg_id` 改为 `seq_id`

### 3.3 统一错误码定义

**当前状态（v5.0）**：

| code | 含义 |
|------|------|
| 0 | 成功 |
| 1 | 设备忙碌 |
| 2 | 参数错误 |
| 3 | 硬件故障 |
| 4 | 超时 |
| 5 | 未授权 |
| 6 | 资源不足 |
| 7 | 不支持 |

**目标状态（v5.2）**：

| code | 含义 | 说明 |
|------|------|------|
| 0 | 成功 | 操作成功完成 |
| 1 | 设备离线 | ESP32 未连接服务器 |
| 2 | 设备忙 | 正在执行其他操作 |
| 3 | 参数错误 | 命令格式或参数无效 |
| 4 | 不支持 | 不支持的命令或操作 |
| 5 | 超时 | 等待响应超时 |
| 6 | 硬件故障 | 硬件异常或不可用 |
| 7 | 资源已满 | 指纹/NFC 存储已满 |
| 8 | 未认证 | 用户未登录或权限不足 |
| 9 | 重复消息 | seq_id 重复（防重放） |
| 10 | 内部错误 | 未知内部异常 |

**修改内容**：
1. 更新错误码映射表
2. 更新 App 端错误提示文案

**涉及文件**：
- `core/constants/error_codes.py`（新建或更新）
- App 端错误处理逻辑

---

### 3.4 log_report 格式变更

**当前状态（v5.0）**：
```json
{
    "type": "log_report",
    "ts": 1702234567890,
    "data": {
        "method": "finger",
        "uid": 5,
        "result": true,
        "fail_count": 0
    }
}
```

**目标状态（v5.2）**：
```json
{
    "type": "log_report",
    "ts": 1702234567890,
    "data": {
        "method": "finger",
        "status": "success",
        "uid": 5,
        "fail_count": 0,
        "lock_time": 0
    }
}
```

**变更说明**：

| 字段 | v5.0 | v5.2 | 说明 |
|------|------|------|------|
| result | bool | 移除 | 改用 status 字段 |
| status | - | string | `success`/`fail`/`locked` |
| lock_time | - | int | 剩余锁定时间（分钟） |

**status 取值**：

| status | 说明 | uid 含义 | fail_count | lock_time |
|--------|------|----------|------------|-----------|
| `success` | 开锁成功 | 用户 ID | 0 | 0 |
| `fail` | 认证失败 | 用户 ID（0xFF=无法识别） | 1-5 | 0 |
| `locked` | 设备锁定 | 无意义 | 0 | 剩余锁定时间 |

**修改内容**：
1. 更新 `logReportHandler.py` 解析逻辑
2. 更新数据库表结构（新增 `status`, `lock_time` 字段）
3. 更新 App 转发消息格式

**涉及文件**：
- `core/handle/textHandler/logReportHandler.py`
- 数据库迁移脚本

---

### 3.5 新增消息类型处理

#### 3.5.1 esp32_ack（命令已收到确认）

**消息格式**：见 3.2.1

**处理逻辑**：
1. 解析 `seq_id`、`code`、`msg`
2. 更新命令状态为"已送达"
3. 可选：转发给 App

**涉及文件**：
- 新增 `core/handle/textHandler/esp32AckHandler.py`

#### 3.5.2 door_opened_report（开门日志）

**消息格式**：
```json
{
    "type": "door_opened_report",
    "ts": 1702234567890,
    "data": {
        "method": "finger",
        "source": "outside"
    }
}
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| method | string | 开锁方式 |
| source | string | `outside`/`inside`/`unknown` |

**处理逻辑**：
1. 存储到数据库（新表或扩展 unlock_logs）
2. 转发给 App

**涉及文件**：
- 新增 `core/handle/textHandler/doorOpenedReportHandler.py`
- 数据库表设计

#### 3.5.3 password_report（密码上报）

**消息格式**：
```json
{
    "type": "password_report",
    "ts": 1702234567890,
    "data": {
        "password": "123456"
    }
}
```

**处理逻辑**：
1. 转发给请求查询的 App
2. 不存储到数据库（安全考虑）

**涉及文件**：
- 新增 `core/handle/textHandler/passwordReportHandler.py`

#### 3.5.4 query（查询命令）【Server 下发】

**消息格式**：
```json
{
    "type": "query",
    "seq_id": "1702234567890_0",
    "command": "sensors"
}
```

**command 取值**：

| command | 说明 |
|---------|------|
| `sensors` | 查询传感器（电量、光照） |
| `status` | 查询状态（锁、补光灯） |

**处理逻辑**：
1. 接收 App 的查询请求
2. 构建 query 消息下发给 ESP32
3. 等待 `esp32_ack` + `ack` + `status_report`
4. 将 `status_report` 转发给 App

**涉及文件**：
- 新增查询命令下发逻辑
- 更新 App 协议文档

### 3.6 新增事件类型

**当前状态（v5.0）**：

| `door_closed` | 门关闭 | 无 |
| `lock_success` | 自动上锁成功 | 无 |
| `bolt_alarm` | 锁舌未到位报警 | 无 |

**修改内容**：
1. 更新 `eventReportHandler.py` 支持新事件类型
2. 更新数据库事件类型枚举
3. 更新 App 端事件展示

**涉及文件**：
- `core/handle/textHandler/eventReportHandler.py`
- 数据库迁移脚本

## 四、数据库变更

### 4.1 unlock_logs 表更新

**新增字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| status | VARCHAR(16) | 状态：success/fail/locked |
| lock_time | INT | 剩余锁定时间（分钟） |

**迁移脚本**：
```sql
ALTER TABLE unlock_logs 
ADD COLUMN status VARCHAR(16) DEFAULT 'success',
ADD COLUMN lock_time INT DEFAULT 0;

-- 迁移旧数据
UPDATE unlock_logs SET status = CASE WHEN result = 1 THEN 'success' ELSE 'fail' END;
```

### 4.2 新增 door_opened_logs 表

```sql
CREATE TABLE door_opened_logs (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    device_id VARCHAR(64) NOT NULL,
    method VARCHAR(16) NOT NULL,
    source VARCHAR(16) NOT NULL,
    created_at DATETIME NOT NULL,
    INDEX idx_device_time (device_id, created_at)
);
```

### 4.3 device_events 表更新

**新增事件类型**：
- `door_closed`
- `lock_success`
- `bolt_alarm`

## 六、实现优先级

### P0 - 必须实现（兼容性）

1. **esp32_ack 处理** - ESP32 已开始发送，服务器必须能处理

3. **新增事件类型** - door_closed, lock_success, bolt_alarm
