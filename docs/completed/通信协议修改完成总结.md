## 二、修改原因

### 2.1 face_result 不需要两级确认

**原因**：
1. face_result 是服务器主动推送的识别结果，不是用户发起的命令
2. 开锁结果通过 log_report 上报即可
3. 不需要 seq_id 和两级确认机制

**协议设计原则**：
- 用户命令（lock_control, query, dev_control, user_mgmt）需要两级确认
- 服务器推送（face_result）不需要确认

### 2.2 query 命令已完全实现

**验证结果**：
- ✅ 接收 query 命令并解析 seq_id
- ✅ 立即发送 esp32_ack（第一级确认）
- ✅ 创建 PendingCommand 并保存
- ✅ 发送 UART 查询命令到 STM32
- ✅ 在收到 RPT_ENV/RPT_STATE 后发送 ack（第二级确认）
- ✅ 支持超时处理

1. **正常识别流程**
   - 触发：门铃/PIR
   - 服务器返回：result="known", granted=true
   - 预期：ESP32 发送开锁命令，上报 log_report

2. **陌生人拒绝**

   - 服务器返回：result="no_face"
   - 预期：ESP32 不开锁，播放提示语音

4. **识别错误**
   - 服务器返回：result="error"
   - 预期：ESP32 不开锁，记录错误

### 4.2 query 命令测试用例

1. **sensors 查询**
   - 服务器发送：{"type":"query","seq_id":"xxx","command":"sensors"}
   - 预期：ESP32 发送 esp32_ack → 查询 STM32 → 上报 status_report → 发送 ack

2. **status 查询**
   - 服务器发送：{"type":"query","seq_id":"xxx","command":"status"}
   - 预期：ESP32 发送 esp32_ack → 查询 STM32 → 上报 status_report → 发送 ack

3. **超时场景**
   - STM32 无响应
   - 预期：5 秒后发送 ack(code=5, msg="Timeout")

4. **无效命令**
   - 服务器发送：{"type":"query","seq_id":"xxx","command":"invalid"}
   - 预期：ESP32 发送 esp32_ack → 立即发送 ack(code=4, msg="Unknown query command")

## 七、关键要点总结

### 7.1 协议设计原则

| 消息类型 | 是否命令 | 需要 seq_id | 需要两级确认 |
|----------|----------|-------------|--------------|
| face_result | ❌ 服务器推送 | ❌ | ❌ |
| lock_control | ✅ 用户命令 | ✅ | ✅ |
| query | ✅ 用户命令 | ✅ | ✅ |
| dev_control | ✅ 用户命令 | ✅ | ✅ |
| user_mgmt | ✅ 用户命令 | ✅ | ✅ |

### 7.2 两级确认机制

**第一级（esp32_ack）**：
- 时机：收到命令后立即发送
- 目的：确保 ESP32 收到命令，避免网络丢包
- 内容：code=0, msg="received"

**第二级（ack）**：
- 时机：命令执行完成后发送
- 目的：确保 STM32 执行完成，反映真实结果
- 内容：code=执行结果, msg=结果描述

### 7.3 修改要点

1. **face_result 简化**
   - 移除 seq_id 解析
   - 移除两级确认
   - 保持异步处理

2. **query 命令完整**
   - 已实现接收和处理
   - 已实现两级确认
   - 已实现超时处理

3. **文档一致性**
